# SuperLingo 实现步骤

> 双语超市商品翻译后端 —— 面向对象设计 → 数据库建模 → Java 后端实现 → 部署测试 的完整落地文档

---

## 1. 项目概述

SuperLingo 是一个帮助在英文国家生活的华人快速识别超市商品的工具：手机浏览器扫码商品条形码，即可获取该商品的中英双语信息（中文为主）。数据初始来源对接 Open Food Facts 官方接口，并通过「首扫落库 + 人工修正」实现数据本地化与纠错闭环。

它的运作流程非常贴近生活：

* **用户扫码**：用户在手机网页上开启摄像头，对准商品条形码（Barcode）即可扫码。


* **展示中文**：程序识别条形码后，会向用户展示该商品的基本信息，最重要的是提供中文翻译。


* **外部获取**：这些信息最初是从一个叫 Open Food Facts 的外部公开网站获取的。


* **自动保存**：因为每次都去外部网站查会比较慢，而且有些翻译不准，所以一旦有人首扫了某个新商品，我们就会把它永久保存在自己的数据库里。


* **人工纠错**：系统有一个需要密码登录的“管理员后台”。管理员可以在后台手动修改和完善那些翻译不够好的商品信息。一旦修改过，以后任何人再扫这个条形码，系统都会优先显示我们修改过的本地数据。


* **数据统计**：后台还会默默记录每一个条形码被扫了多少次，以及每次扫码的用户的 IP 地址，方便我们发现哪些商品最热门。


### 1.1 功能需求

**C 端（用户扫码端）**
1. 手机浏览器打开网址，网页自动请求摄像头权限，唤起取景框；
2. 对准商品条形码自动识别；
3. 识别成功后弹出结果卡片，展示中英对照的商品信息。

**数据流转与治理（Human-in-the-loop）**
4. 新商品首次被扫码时，从 Open Food Facts 抓取数据并「首扫落库」永久保存到本地数据库；
5. 后台可对翻译生硬的中文信息进行人工修正，修正后该条码永远以本地数据为准，不再请求外部接口。

**B 端（管理后台）**
6. 独立管理员登录，密码校验通过后方可进入；
7. 扫码埋点：记录每次扫码的条码、用户 IP、时间戳；
8. 热度统计：展示每个条码累计被扫频次（发现热门商品）。

## 3. 面向对象设计

这个程序比较简单，从功能描述部分可以看到有**商品**、**历史记录**、**管理员**三个实体就可以了，当然这三个实体会直接对应代码中的三个类，也是数据库中的三个数据表。

每个类有哪些属性呢？其中最简单的是管理员类，账户、密码是必不可少的属性，当然还可以考虑增加头像、昵称等字段。

历史记录也很容易想到需要哪些属性，记录条形码（可关联商品类）、IP 地址、扫码时间即可。

比较麻烦的是商品，由于我们自身精力有限，无法去超市或厂家逐一比对不同商品有哪些属性，所以此处我们暂按着自己的认知罗列一些属性，后续在整个系统维护过程中遇到哪些需要补充再完善。目前能想到的属性有：商品条形码、中文名称、英文名称、商品图片、数据来源（API或人工修正）。

三个实体对应代码中的三个类、数据库中的三张表。

```Java
// 管理员
public class AdminUser {
    private Integer id;
    private String username;
    private String passwordHash;   // 存 BCrypt 哈希，不存明文
}

// 商品
public class Product {
    private String barcode;   // 条形码，全宇宙唯一，直接作主键
    private String nameZh;    // 中文名称
    private String nameEn;    // 英文名称
    private String imageUrl;  // 商品图片
    private String source;    // AUTO=API 抓取 / MANUAL=人工修正
}

// 扫码流水
public class ScanLog {
    private Integer id;            // 自增流水号
    private String barcode;        // 关联商品的外键
    private String ipAddress;      // 用户 IP
    private Timestamp scannedAt;   // 扫码时间
}
```

### 6.1 项目代码结构

在这个项目中，你会看到很多没见过的名词，比如 Controller、Service、Dao。不要怕，这就是 Java Spring Boot 框架经典的“分层架构”。
**我们可以把这个 Java 后端程序想象成一家“餐厅”**，`../src/main/java/com/guanngxu/superlingo` 目录下的文件夹就是餐厅里的不同部门：

* **`entity` (食材)**：就是我们上面提到的 Product、ScanLog 等，单纯用来装载数据的对象。


* **`dao` (仓库管理员)**：Data Access Object，专门负责和数据库打交道。它只做一件事：写 SQL 语句，把 `entity`（食材）存进数据库，或者从数据库拿出来给别人用。


* **`client` (外部采购员)**：如果仓库里找不到你要的商品数据，就需要去外部进货。`OpenFoodFactsClient.java` 就是专门负责通过网络去外部网站（Open Food Facts）抓取数据的代码。


* **`service` (主厨)**：核心的大脑！比如 `ScanService.java`。它负责制定做菜逻辑：首先让 `dao` 去数据库找商品，如果找不到，就派 `client` 去外部网抓取；抓到后让 `dao` 存进数据库，最后再让 `dao` 记录一条扫码日志。


* **`controller` (服务员)**：负责和真正的顾客（前端手机网页）打交道。比如 `ScanController.java`。它接收手机浏览器发来的请求指令，把指令传给 `service`（主厨），主厨处理完后，`controller` 把结果端出去给前端用户。


* **其他辅助部门**：
* `config`：餐厅的规章制度，比如配置项。


* `common`：统一标准，比如 `ApiResponse.java` 规定了端给顾客的盘子（返回给前端的数据格式）必须长什么样。


* `utils`：小工具箱，比如有个工具专门用来提取用户的真实 IP 地址。

## 6. 核心实现细节

### 6.1 Gson 接管 JSON（`config/GsonConfig.java`）

- 提供一个 `Gson` bean；Spring Boot 会自动将其包装为 `GsonHttpMessageConverter`，接管所有 `@ResponseBody` / `@RequestBody`。
- 自定义 `java.util.Date` / `java.sql.Timestamp` 序列化为 ISO-8601 字符串（`DateTimeFormatter.ISO_INSTANT`），前端拿到的是 `2026-10-02T07:08:54.526179Z` 这样的可读时间，而非时间戳数字。

### 6.2 统一响应体（`common/ApiResponse.java`）

所有接口统一返回：

```json
{ "code": 200, "message": "success", "data": { ... } }
```

- `ApiResponse.ok(data)`：成功，`code=200`。
- `ApiResponse.error(code, msg)`：失败，`data=null`。例如商品未找到返回 HTTP 404 + `{code:404, message:"未找到商品信息"}`。

### 6.3 客户端 IP 提取（`utils/ClientIpUtil.java`）

部署在反向代理（Nginx / Koyeb / Oracle Cloud）之后时，真实 IP 在 `X-Forwarded-For` 头里。提取顺序：

1. `X-Forwarded-For`（取第一个，可能是 `client, proxy1, proxy2`）
2. `X-Real-IP`
3. `request.getRemoteAddr()`（兜底）

### 6.4 扫码核心流程（`service/ScanService.java`）

```
processScan(barcode, ip):
  1. product = productDao.findByBarcode(barcode)     // L1 缓存命中？
  2. 若为 null：
       product = offClient.fetch(barcode)            // 调 Open Food Facts
       若抓到：productDao.saveOrUpdate(product)      // 首扫落库
  3. 若 product 非 null：scanLogDao.insert(...)      // 记录流水（外键要求商品已在库）
  4. return product                                  // null 则 Controller 返回 404
```

- 缓存命中（本地已有数据，无论 `AUTO` 还是 `MANUAL`）→ 直接返回，不再请求外部接口，这正是「人工修正后以本地数据为准」的实现基础。
- `saveOrUpdate` 使用 PostgreSQL 的 `INSERT ... ON CONFLICT (barcode) DO UPDATE SET ...`（UPSERT），有则更新、无则插入。

### 6.5 外部数据抓取（`client/OpenFoodFactsClient.java`）

- 请求 `https://world.openfoodfacts.org/api/v2/product/{barcode}?fields=product_name,product_name_zh,image_url,image_front_url`。
- 只取必要字段（`fields` 参数），减少响应体积。
- 解析 `status`：`1` 表示找到，`0` 表示未找到该条码。
- 中文名 `product_name_zh` 缺失时回退到英文名 `product_name`。
- 图片取 `image_url`，为空再取 `image_front_url`。
- 任何异常（超时、非 200、解析失败）都返回 `null`，由上层当作「未找到」处理，保证接口不会因外部依赖抖动而 500。

### 6.6 管理员鉴权（`service/AdminAuthService.java` + `config/AdminInitializer.java`）

- **密码哈希**：`BCryptPasswordEncoder`，数据库只存哈希，登录时用 `matches(明文, 哈希)` 校验。
- **Token**：登录成功后生成一个随机 token（`Base64(UUID:username)`），存入内存 `ConcurrentHashMap`（`token -> username`）。
- **默认管理员**：应用启动时，若 `admin_users` 表为空，自动插入默认账号。

  | 项 | 默认值 | 覆盖方式 |
  |----|--------|----------|
  | 用户名 | `admin` | 环境变量 `ADMIN_USERNAME` |
  | 密码 | `admin123` | 环境变量 `ADMIN_PASSWORD` |

- 初始化逻辑包在 `try-catch` 中：数据库暂不可达时不阻断应用启动。

## 7. RESTful API 接口设计

统一前缀 `/api/v1`。

### 7.1 C 端

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/scan/{barcode}` | 扫码查询并记录日志 |

请求示例：`GET /api/v1/scan/0028400199148`

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "barcode": "0028400199148",
    "nameZh": "乐事经典原味薯片",
    "nameEn": "Lay's Classic Potato Chips",
    "imageUrl": "https://images.openfoodfacts.org/...",
    "source": "MANUAL"
  }
}
```

未找到（条码不存在且 OFF 也查不到）：

```json
{ "code": 404, "message": "未找到商品信息", "data": null }   // HTTP 404
```

### 7.2 B 端（管理后台）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/admin/login` | 管理员登录 |
| GET | `/api/v1/admin/products` | 商品列表（浏览所有已入库商品） |
| POST | `/api/v1/admin/products/{barcode}` | 人工修正商品信息 |
| GET | `/api/v1/admin/stats/hot?limit=20` | 热门商品排行榜 |
| GET | `/api/v1/admin/logs/{barcode}` | 某商品的扫码流水 |

**登录**：

```json
POST /api/v1/admin/login
{ "username": "admin", "password": "admin123" }

→ { "code": 200, "message": "success", "data": { "token": "..." } }
// 用户名或密码错误 → HTTP 401
```

**人工修正**（修正后 `source` 自动置为 `MANUAL`）：

```json
POST /api/v1/admin/products/0028400199148
{ "nameZh": "乐事经典原味薯片", "nameEn": "Lay's Classic Potato Chips", "imageUrl": "..." }
```

**热门排行榜**：

```json
GET /api/v1/admin/stats/hot
→ { "code": 200, "data": [ { "barcode": "...", "nameZh": "...", "nameEn": "...", "scanCount": 3 } ] }
```

**扫码流水**（IP + ISO 时间戳）：

```json
GET /api/v1/admin/logs/0028400199148
→ { "code": 200, "data": [ { "id": 3, "barcode": "...", "ipAddress": "...", "scannedAt": "2026-10-02T07:08:54.526179Z" } ] }
```

## 8. 运行与部署

### 8.1 部署平台

后端可部署到 Koyeb 或 Oracle Cloud。部署时通过平台的环境变量面板注入 `SUPABASE_DB_URL`、`SUPABASE_DB_USER`、`SUPABASE_DB_PASSWORD`，以及 `ADMIN_USERNAME` / `ADMIN_PASSWORD`。

### 9.3 前后端对接

- 已开启 CORS（`config/WebConfig.java`），允许 `/api/**` 跨域，前端可独立部署。生产环境建议把 `allowedOriginPatterns("*")` 收敛为实际前端域名。
- 前端（扫码页 / 后台页）由 AI 另行编写，调用上述 API 即可。

## 10. 测试验证清单

按以下顺序做端到端验证：

1. **启动**：日志出现 HikariPool 连接成功、默认管理员初始化。
2. **登录**：`POST /admin/login` 正确密码返回 token，错误密码返回 401。
3. **扫码落库**：`GET /scan/{真实条码}` 首次请求从 OFF 抓取并落库（`source=AUTO`）。
4. **缓存命中**：再次扫同一码，返回本地数据，不再请求外部接口。
5. **人工修正**：`POST /admin/products/{barcode}` 修正中文名，`source` 变 `MANUAL`。
6. **修正优先**：再扫该码，返回的是人工修正后的数据。
7. **热度统计**：`GET /admin/stats/hot` 的 `scanCount` 与扫码次数一致。
8. **流水查询**：`GET /admin/logs/{barcode}` 返回每次扫码的 IP 与时间戳。
